==================================================
一、重构目标
==================================================

当前链路：

用户问题
→ retrieval/chat 二分类
→ Query Rewrite
→ 全库 Chunk FTS + Embedding
→ RRF/MMR
→ Rerank
→ Generation
→ Citation Validation

存在两个核心问题：

问题 A：
无法稳定判断用户是在闲聊还是询问自己的本地资料。

例如：

“我的简历里面有什么？”
“我之前那个项目用了什么技术？”
“上次那个合同是多少钱？”
“这个文件主要讲什么？”

这些问题必须优先理解为用户正在指向本地实体/文件，而不是只根据字面判断 retrieval/chat。

问题 B：
用户询问“我的简历”时，系统实际上是在全库搜索“简历”这个词。

例如用户：

“我的简历里面有哪些项目？”

可能真正的简历文件名是：

周晨.pdf
大模型开发工程师-周晨.pdf
应聘材料V3.docx

正文甚至可能没有“简历”二字。

因此绝对不能：

query = “我的简历里面有哪些项目”
→ 全库 Chunk Retrieval

需要：

理解用户目标是 resume
→ 找到哪份文件属于用户的 resume
→ 锁定 file_id
→ 再在该文件内部查询“项目经历”。

==================================================

将链路改为：

用户问题
↓
1. Source Router
↓
2. Query Parser
↓
3. Context / Memory Resolver
↓
4. Document Resolver
↓
5. Operation Router
↓
6. Retrieval Planning
↓
7. Scoped Retrieval
↓
FTS + Embedding + RRF/MMR
↓
8. Rerank
↓
9. Generation
↓
10. Citation Validation
↓
11. Session Context Update
↓
12. Memory Candidate Writer

注意：

Memory 只帮助理解和定位。

Memory 绝对不能作为最终事实证据。

最终回答仍然必须从原始文件 Chunk 获取证据并使用现有 Citation Validation。

==================================================
三、第一阶段：废除旧 retrieval/chat 二分类
==================================================

不要再让一个小模型直接输出：

retrieval
chat

改成 Source Router：

LOCAL
GENERAL
AMBIGUOUS

定义：

LOCAL：
回答明显涉及用户自己的文件、资料、文档、项目、合同、简历、记录、之前查看过的内容，或者依赖本地资料才能回答。

GENERAL：
普通知识问答、寒暄、纯聊天，不需要用户本地资料。

AMBIGUOUS：
存在指代，但仅凭当前问题无法判断，例如：

“那个怎么样？”
“第二个呢？”
“里面写了什么？”
“之前那个呢？”

AMBIGUOUS 必须结合 session context / recent referenced files 再判断。

禁止使用：

“无法确定 → chat”

新的原则：

无法确定 → AMBIGUOUS。

--------------------------------------------------
Source Router Prompt
--------------------------------------------------

system:

你是翻翻的“信息来源路由器”。

你的任务不是回答问题，而是判断回答用户当前问题是否需要使用用户的本地资料。

只输出符合 JSON Schema 的对象，不要解释。

分类只有：

LOCAL：
用户的问题明确或高度可能需要读取用户自己的文件、文档、资料库、历史资料或当前正在查看的文件才能回答。

GENERAL：
问题可以作为普通聊天或通用知识问题回答，不需要读取用户本地资料。

AMBIGUOUS：
存在“这个、那个、里面、刚才的、之前的、第二个、它”等指代，或者仅凭当前一句无法确定是否需要本地资料，需要结合当前会话上下文判断。

判断原则：

1. 出现“我的”“我之前”“我的文件”“我的资料”“我的简历”“我的合同”“我的项目”“之前那份”“这个文件”等表达时，优先判断 LOCAL。
2. 用户询问某份文档中的内容，判断 LOCAL。
3. 用户询问自己过去记录、工作、学习、项目、文件中的内容，判断 LOCAL。
4. 通用知识问题判断 GENERAL。
5. 纯寒暄判断 GENERAL。
6. 指代不清时判断 AMBIGUOUS，禁止为了安全直接判断 GENERAL。

输出：

{
  "source": "LOCAL | GENERAL | AMBIGUOUS",
  "confidence": 0.0-1.0
}

四、第二阶段：新增 Query Parser
==================================================

LOCAL 或解析后的 AMBIGUOUS 不要直接进入 Query Rewrite。

先生成结构化 QueryPlan。

统一结构：

{
  "source": "LOCAL",
  "intent": "...",
  "operation": "...",

  "target": {
    "reference": null,
    "document_type": null,
    "document_name": null,
    "owner": null,
    "entity_type": null,
    "entity_name": null
  },

  "content_query": null,

  "filters": {
    "time": null,
    "file_type": null,
    "path": null
  },

  "requires_document_resolution": false,
  "requires_full_document": false,
  "confidence": 0.0
}

intent 第一版只支持：

DOCUMENT_FIND
DOCUMENT_QA
DOCUMENT_SUMMARY
LIBRARY_QA
MULTI_DOCUMENT_QA
COMPARE_DOCUMENTS
GENERAL_CHAT

operation 支持：

FIND
QA
SUMMARY
EXTRACT
COMPARE

示例：

用户：
“我的简历里面有哪些项目？”

输出：

{
  "source": "LOCAL",
  "intent": "DOCUMENT_QA",
  "operation": "EXTRACT",
  "target": {
    "reference": "我的简历",
    "document_type": "resume",
    "document_name": null,
    "owner": "self",
    "entity_type": null,
    "entity_name": null
  },
  "content_query": "项目经历",
  "filters": {},
  "requires_document_resolution": true,
  "requires_full_document": false,
  "confidence": 0.96
}

用户：
“我的简历有什么内容？”

输出：

{
  "source": "LOCAL",
  "intent": "DOCUMENT_SUMMARY",
  "operation": "SUMMARY",
  "target": {
    "reference": "我的简历",
    "document_type": "resume",
    "owner": "self"
  },
  "content_query": null,
  "requires_document_resolution": true,
  "requires_full_document": true
}

用户：
“我的资料里面有没有提到 LangGraph？”

输出：

{
  "source": "LOCAL",
  "intent": "LIBRARY_QA",
  "operation": "QA",
  "target": {},
  "content_query": "LangGraph",
  "requires_document_resolution": false,
  "requires_full_document": false
}

--------------------------------------------------
Query Parser Prompt
--------------------------------------------------

system:

你是翻翻的“本地资料查询解析器”。

你的任务是理解：
1. 用户想对什么对象操作；
2. 用户真正想知道什么；
3. 是否明确指定或隐含指定某个文档；
4. 是否需要阅读整份文档。

不要直接回答问题。
不要生成检索结果。
只输出规定 JSON。

特别注意：

“我的简历里有没有 LangGraph”

不能把“我的简历 LangGraph”整体作为搜索关键词。

必须拆成：

target.document_type = resume
target.owner = self
content_query = LangGraph

“我的简历有什么内容”

属于 DOCUMENT_SUMMARY，而不是普通关键词检索。

“我的简历在哪里”

属于 DOCUMENT_FIND。

“所有文件里哪些提到了 RAG”

属于 LIBRARY_QA。

“比较我两个简历版本”

属于 COMPARE_DOCUMENTS。

至少包括：

Memory 不是第二份知识库。

不要复制 Chunk 正文。

Memory 只存：

用户 ↔ 实体 ↔ 文件之间的关系、别名和稳定信息。

SQLite 第一版即可。

新增：

memory_entities

字段建议：

id
entity_type
canonical_name
metadata_json
created_at
updated_at

新增：

memory_relations

字段：

id
subject_type

predicate
object_type
object_id
confidence
status
source_type
source_id
created_at
updated_at

status：

candidate

rejected

新增：

memory_aliases

字段：

id

confidence

source_id

例如：

“我的简历”
→ file:123

Memory 优先级：

user_explicit > user_confirmed > repeated_usage > document_inference > model_inference

严禁：

因为一个 PDF 出现“张三”
→ 自动认定用户叫张三。

七、Document Profile
==================================================

给每个文件增加文件级语义画像。

不要只索引 Chunk。

至少保存：

file_id
document_type
type_confidence
document_title
document_summary
section_titles
entities
keywords
document_embedding
updated_at

document_type 第一版可以支持：

resume
contract
invoice

project_document

learning_material
certificate
report
spreadsheet
other

filename 只作为一个弱信号。

例如：

“大模型开发工程师-周晨.pdf”

可以根据正文判断：

document_type = resume

即使文件名没有“简历”。

Document Profile 必须在文件进入索引时生成，而不是用户问问题时临时全部生成。

已有 Embedding 模型可以负责 document_embedding。

document_embedding 建议由：

document title
+
section titles
+
document summary
+
代表性正文

生成。

==================================================
八、Document Resolver
==================================================

当 QueryPlan：

requires_document_resolution = true

先执行 Document Resolver。

Resolver 输入：

QueryPlan
Memory candidates
Session context
Document Profiles

输出：

{
  "candidates": [
    {
      "file_id": "...",
      "score": 0.94,
      "signals": [
        "memory_alias",
        "document_type",
        "owner_match",
        "embedding"
      ]
    }
  ],
  "resolved_file_ids": [],
  "resolution_confidence": 0.0
}

Resolver 不要只按 filename。

综合：

memory confirmed relation
memory alias
session active file
document_type
document title
entity match
filename/path
document embedding
recent usage

不要先写死精确权重。

实现成可配置 scoring signals。

建议行为：

高置信度且明显唯一：
锁定一个文件。

中置信度：
保留 top 2~3 文件进入候选 scope。

存在两个非常接近的候选：
返回 NEED_CLARIFICATION。

低置信度：
不要错误锁定文件。
退回较宽 scope。

九、必须加入 RetrievalScope
==================================================

统一数据结构：

{
  "file_ids": [],
  "collection_ids": [],
  "document_types": [],
  "entity_ids": [],
  "path_prefixes": [],
  "time_range": null

当前 FTS、Embedding Retrieval 都必须支持同一个 Scope。

例如：

绝对不要再搜：

“我的简历 LangGraph”

==================================================
十、Query Rewrite 只重写 content_query
==================================================

当前 Query Rewrite 不再负责理解目标文件。

它只允许处理：

content_query

例如：

QueryPlan：

target = resume
content_query = “项目经历”

Query Rewrite 只能改：

“项目经历”

不能把 target 又塞回搜索 Query。

如果：

DOCUMENT_SUMMARY

则可以直接跳过普通 Query Rewrite。

==================================================
十一、不同 intent 使用不同 Retrieval Pipeline
==================================================

不要所有请求都：

Chunk Retrieval
→ Rerank
→ top 3

分别实现：

1. DOCUMENT_FIND

只运行 Document Resolver。

不运行普通 Chunk RAG。

2. DOCUMENT_QA

Document Resolver
→ scope 到对应 file
→ Chunk Retrieval
→ Rerank
→ Generation

3. DOCUMENT_SUMMARY

Document Resolver
→ 读取整份文档结构
→ section/chunk 分层处理
→ 聚合摘要

不能只拿 top-3 Chunk。

4. LIBRARY_QA

不限定单文件
→ 全库 Hybrid Retrieval
→ Rerank

5. MULTI_DOCUMENT_QA

先找到相关 Document candidates
→ 再在候选文档集合内部检索

6. COMPARE_DOCUMENTS

先解析两个目标文件
→ 两侧分别取证
→ 再比较

==================================================
十二、优化全库 Retrieval
==================================================

保留现有：

FTS
Embedding
RRF
MMR
Rerank

但增加两级召回思想：

Document-level recall
→ Chunk-level recall

对于没有明确文件目标的 LOCAL 请求，例如：

“我以前哪些文件提到过 LangGraph？”

可以：

第一阶段：

Document Profile / document embedding
→ 找 top N 文件

第二阶段：

仅在这些候选文件中
→ Chunk FTS + Embedding

不要默认让所有 Chunk 永远直接参与竞争。

但需要保留 fallback：

如果 document-level recall 无结果，
允许进行一次 wider chunk retrieval。

==================================================
十三、修复 Rerank 逻辑
==================================================

删除当前：

rerank top-1 < threshold
→ 自动转 chat

逻辑。

因为：

“我的毕业证编号是多少？”

明确是 LOCAL。

即使没搜到，也不代表是聊天。

改成：

Source Router 决定信息来源。

Retrieval 决定是否找到证据。

两者完全解耦。

状态定义：

GENERAL
LOCAL
AMBIGUOUS

以及：

EVIDENCE_FOUND
NO_EVIDENCE
NEED_CLARIFICATION

如果：

LOCAL + NO_EVIDENCE

返回：

当前资料中没有找到足够依据。

禁止转成闲聊回答。

==================================================
十四、Generation 和 Citation Validation 尽量保持
==================================================

现有严格证据模式原则保留。

所有事实仍必须关联 S#。

Memory：
不能变成 S#。

Document Profile：
不能直接变成 S#。

Session History：
不能变成 S#。

只有原始文件证据 Chunk 才可以成为 Citation Evidence。

==================================================
十五、Memory Writer
==================================================

问答结束后增加异步 Memory Candidate Writer。

但禁止所有问答自动写 Memory。

允许写 Memory 的事件主要包括：

1. 用户明确表达：

“这是我的简历。”

2. 用户明确确认候选：

“对，就是第一份。”

3. 用户给某文件起别名：

“以后这个就叫法律项目。”

4. 同一关系被多次明确使用。

用户普通问题：

“Transformer是什么？”

不产生 Memory。

--------------------------------------------------
Memory Writer Prompt
--------------------------------------------------

system:

你是翻翻的 Memory Candidate Extractor。

你的任务不是总结对话，而是判断本轮用户是否明确提供了值得长期保存的“实体关系或别名”。

只记录：

1. 用户明确表达的关系
2. 用户明确确认的关系
3. 用户给文件/项目/实体定义的别名

不要根据猜测建立用户身份事实。
不要记录普通聊天内容。
不要记录临时问题。
不要复制文档正文。

输出：

{
  "should_write": true/false,
  "memories": [
    {
      "type": "relation | alias",
      "subject": "...",
      "predicate": "...",
      "object": "...",
      "alias": null,
      "confidence": 0.0,
      "status": "candidate | confirmed"
    }
  ]
}

==================================================
十八、开发约束
==================================================

1. 不要大规模重写现有已经工作的 Citation Validation。
2. 保留现有 FTS + Embedding + RRF + MMR + Rerank。
3. 在现有结构上增加 Document-level / Memory-level resolution。
4. 所有 DB 修改使用 migration。
5. 不要删除旧字段造成已有数据库不可升级。
6. 新逻辑必须有 fallback。
7. 所有模型失败不得导致应用崩溃。
8. Memory 错误不得阻止普通 Retrieval。
9. Document Resolver 错误不得永久绑定错误关系。
10. 所有长期 Memory 必须可删除、可修改、可失效。
11. 不允许偷偷上传用户信息。
12. 保持完全本地运行。
13. 不要仅修改 ask-flow.html；修改真实实现后同步更新 ask-flow.html。
14. 不要为了通过测试硬编码“简历”“周晨”等案例。
15. 文档类型、Intent、Operation 必须使用统一 enum / typed struct。
16. Prompt 输出尽可能使用 JSON Schema / grammar 约束，而不是字符串猜测解析。

==================================================
二十、最终验收标准
==================================================

改造完成后，以下问题必须得到结构上正确的处理：

“我的简历有什么内容？”
→ 找到简历文件 → 整文摘要

“我的简历里面有哪些项目？”
→ 找到简历文件 → 文件内部搜索项目经历

“我的简历里有没有 LangGraph？”
→ 找到简历文件 → 文件内部查询 LangGraph

“之前那个文件第二段讲什么？”
→ Session Context → 当前文件 → 查询第二段

“我以前哪些资料提到 RAG？”
→ 全库资料请求 → Document shortlist → Chunk retrieval

“你好”
→ GENERAL → 普通聊天

“Transformer是什么？”
→ GENERAL → 普通知识问答

“我的资料里面对 Transformer 是怎么写的？”
→ LOCAL → 本地资料检索

“我的简历有没有身份证号？”
→ LOCAL → 简历文件 → NO_EVIDENCE
→ 不允许转换成闲聊

最终目标不是简单提高 RAG 相似度，而是让整个系统从：

Query → 相似 Chunk

升级成：

Query
→ 理解用户在指什么
→ 找到目标实体/文件
→ 判断用户想对它做什么
→ 确定检索范围
→ 找原始证据
→ 回答并引用。
