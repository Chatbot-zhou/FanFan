# RAG 链路故障诊断与改进方案

> 诊断日期：2026-08-14　来源：运行日志 + 数据库实际问答记录 + 真实知识库实测复现

## 一、现象

用户发「你好」，系统返回了一篇论文的"摘要综述"（含 `claims`/`citation_ids` JSON 原文），并提示「本次生成结果未通过核验，置信度较低」。

## 二、日志/数据画像（时间线）

| 时间 | 结果 |
|---|---|
| 08-13 07:51 | 检索降级（仅 filename+fts，index_coverage=0）→ 拒绝回答 ✅ 正常 |
| 08-13 09:32~09:33 | 同问题连败 3 次 `RAG_CITATION_VALIDATION_FAILED`（重试） |
| 08-13 13:11 / 16:34、08-14 04:32 | 均 `RAG_CITATION_VALIDATION_FAILED` |
| 08-14 05:58 | completed 但 `claim_count=0, citation_count=0`（94s，降级） |
| 08-14 10:05 / 10:48 | 「你好」×2：走全链路，55s/27s，`claim_count=0`，展示原始 JSON |

**核心事实：系统至今没有成功产出过一次"通过核验的带引用答案"。** 要么失败，要么降级展示未核验原文。

## 三、根因链（一次「你好」的完整旅程）

### 环节 1：意图路由 —— 三层兜底全部默认"检索"

实测（bge-small-zh 真实编码）：
- 「你好」对闲聊示例 top1 相似度 **0.466 < 0.55 阈值**，margin **0.066 < 0.08** → `Ambiguous`
- Ambiguous 交给 Qwen3-0.6B 仲裁，而：
  - 仲裁 prompt 明确写着 **「拿不准时按检索（retrieval）处理，宁可查资料也不要编造闲聊内容」**——强检索偏置（knowledge.rs `intent_arbitration_prompt`）
  - 0.6B 模型输出 32 token 的 JSON 经常失败/不合法 → `parse_intent_verdict` 返回 None → **`unwrap_or(Intent::Retrieval)` 静默落检索**
- Embedding 不可用/编码失败 → fallback 也是 Retrieval

→ 闲聊判定路径上没有任何一层会兜底到 Chat。**默认值应该反过来：闲聊答错无副作用，检索答错会把资料库内容当答案胡说。**

### 环节 2：检索 —— 门槛被归一化公式破坏，53% 的块"相关"

实测（对 197,601 块全量余弦扫描）：
- 分数公式 `score = (cosine + 1) / 2`（storage.rs:8084），把 bge 的弱相似度膨胀：
  - cosine 0.6 → 0.80（正好过 0.80 的查询相关性门槛）
  - cosine 0.4 → 0.70（正好过 0.70 的候选证据门槛）
- bge-small-zh 对任意中文文本的余弦先验约 0.55~0.65 → 归一化后 0.78~0.83
- **105,118 / 197,601（53%）块 ≥ 0.70 门槛**；top1 归一化 0.803 过 0.80 查询门槛
- top1~top5 分差仅 0.001~0.005 —— **纯噪声差异**，选谁完全随机
- top1~top9 恰好全是论文相关文件（全文定稿.docx、AIGC 统计报告、逐字稿等）——库里文件多、分块密，噪声检索时被随机选中

→ 查询级相关性门槛（0.87/0.80+margin）和候选门槛（0.70）对 bge-small-zh **形同虚设**。「你好」被判定"库里有相关内容"，还"带证据"进了生成环节。

### 环节 3：生成 —— Qwen3-0.6B 扛不住结构化 JSON + 严谨引用

- 生成端要求输出严格 JSON schema（`grounded_answer_json_schema`：claims + citation_ids，`^S[1-9][0-9]*$`）
- 0.6B 模型的典型表现（日志实证）：8/13 连续 3 次 JSON 结构全错、repair 也救不回来（`RAG_CITATION_VALIDATION_FAILED`）
- 「你好」这次：0.6B 拿到 8 个论文证据块后把任务当成了"总结这篇论文"——输出论文摘要、AIGC 检测结论、甚至**致谢片段**（"我打下坚实基础。同时，谨向我的家人致以深切感谢。"）当 claims；同时自己又写了 `"refusal": "当前资料中未..."`——**模型自己都知道不对，但 0.6B 无法拒绝 prompt 的指令**

### 环节 4：核验 —— 让 0.6B 验证 0.6B

- `claim_has_deterministic_support`：要求 ≥72% 字符 bigram 重合——论文 claim 是"改写式"的（"由于…故能…诸种痛点"），过不了
- 于是逐条交给"又是 0.6B"的 LLM 验证器判 SUPPORTED/UNSUPPORTED——0.6B 对"事实句是否被原文支持"的判断极不可靠，全部拒掉
- claims 清空 → 走 `unverified_answer` 降级

### 环节 5：降级展示 —— 把模型原始 JSON 直接怼给用户

- `extract_unverified_text` 拿到的就是模型输出的 JSON 原文（含 `claims`/`citation_ids`），原样展示
- 用户看到的就是一大坨 JSON + 「未通过核验」警告

## 四、改进方案（按优先级）

### P0：修复检索门槛（元凶，改动最小收益最大）

分数公式与门槛不匹配是根因。方案：

1. **改用原始余弦做门槛**，放弃 `(cos+1)/2` 膨胀：
   - 候选证据门槛：`cos ≥ 0.66`（取代归一化 0.70）
   - 查询相关性门槛：`top1 cos ≥ 0.72 且 margin ≥ 0.01`（取代归一化 0.80/0.87）
2. **用真实数据标定，不要拍脑袋**：写标定脚本，用 eval/qa-fixtures 的 38 道正例 + 一批寒暄/无关查询负例，画出正负 cosine 分布，取分界点（现有 `_dbg_eval.rs` 和 `eval/dbg_nihao.py` 可复用）
3. **加 top1-top2 gap 约束**：gap < 0.01 → 判定"无真实命中"→ 拒绝回答（现在 top1~5 差 0.001~0.005，就是"没有命中"的指纹）
4. **超短查询（≤4 字）用更严门槛**，或直接并入 P1 的白名单

### P1：闲聊分流（兜底反转 + 白名单）

1. **纯寒暄白名单**：`你好|您好|嗨|哈喽|谢谢|再见|晚安|在吗|吃了吗|在干嘛|…`（正则 + 字符数 ≤ 8）→ 直接 Chat，不进路由、不进检索
2. **兜底反转**：Ambiguous → 仲裁失败 → **默认 Chat 而不是 Retrieval**（`route_question` 的 `unwrap_or`）
3. **仲裁 prompt 去掉偏置**：「拿不准时按检索处理，宁可查资料也不要编造」改为中性描述（0.6B 本来就不稳定，不要再推一把）
4. 路由阈值 `ROUTE_CONFIDENCE_THRESHOLD` 0.55 → 实测标定（bge 对闲聊句区分度差，可能要降到 0.45~0.50 或对闲聊类单独调）

### P2：生成/核验适配 0.6B（决定"能答"的下限）

1. **生成改 extractive 风格**：prompt 明确「直接摘录原文句子，不要改写、不要总结、不要添加连接词」——改写越少，确定性核验越容易过（现在 72% bigram 重合对"改写式"答案天然不利）
2. **核验优先级反转**：确定性算法优先且更宽松（72% → 60%，或"claim 完全出现在证据中"直接过）；LLM 验证器只在确定性判定失败时调用
3. **批量核验**：8 条 claim 一次 prompt 全部判断，替代逐条串行（省 6~8 次 0.6B 推理 ≈ 每次 ~1-2s）
4. **重试上限**：结构 repair 只允许 1 次；不要自动整体重试（现在 09:32 连打了 3 次）
5. **考虑降低 schema 复杂度**：若 0.6B 持续失败，把「逐 claim 带 citation_ids」降为「整段答案 + 末尾统一 [S1]…[S8] 引用列表」

### P3：核验失败的降级策略

1. **绝不再展示模型原始 JSON**：`unverified_answer` 的 fallback_text 若含 JSON 骨架，先剥离为纯文本（去掉大括号/引号/字段名），或直接转「抱歉，未找到足够依据，你可以换个问法」
2. 降级前先判断 `refusal` 字段：模型自己写了 refusal → 直接展示 refusal 文案
3. 可选：展示检索到的证据原文块（标注文件），让用户看到"系统读了什么"，比展示 JSON 强

### P4：性能（顺带）

- 单次 27~94s 主要浪费在：逐条 LLM 核验 + 失败重试链。P2 的批量核验 + 重试上限可直接砍掉一半以上
- usearch 检索 3~4s 可接受；`understanding` 阶段的 LLM 查询改写对无历史提问可跳过（现在无历史时也会走一次？——检查 `is_natural_language_query` 是否生效）

### P5：验证闭环（防止再犯）

1. 用 eval/qa-fixtures 38 题建立回归基线：目标 = 核验通过率 ≥ 80%、引用命中正确文件 ≥ 70%
2. fixtures 增加负例：寒暄（你好/谢谢）、无关问题（今天天气）、乱码查询
3. 每次改门槛/路由，先跑 `evaluate_qa_fixtures.rs` 再合入

## 五、落地顺序

```
P0 检索门槛校准（含标定脚本）  → 立即可做，半天
P1 闲聊白名单 + 兜底反转      → 立即可做，2~3 小时
P2 extractive 生成 + 批量核验  → 1 天
P3 降级策略                   → 2~3 小时
P4 性能                       → 顺带
P5 回归基线                   → 与 P0 同步建
```
